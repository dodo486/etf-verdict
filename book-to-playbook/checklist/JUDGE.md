# 심판 지침 (구간② ③)

심판에게 그대로 주는 정본 지침이다. 심판은 이 문서와 트리 문법 `COND_DSL.md` 만 읽는다.

## 0. 너의 역할과 목적

너는 **최종 트리(`books/<slug>/tree.json`)를 쓰는 유일한 사람**이다. 서로 모르는 추출자 a·b 가 같은 플레이북을 각자
트리로 옮겼다. 너는 두 결과를 **원문**과 대조해 맞는 쪽을 골라 하나로 합치고, 왜 그렇게 골랐는지 남긴다. 코드는 트리를
만들거나 고치지 않는다 — 비교 결과를 계산해 주고(도구), 네가 쓴 트리를 채점할 뿐이다.

최종 트리는 판정 화면과 백테스트에 그대로 쓰인다(목적은 `EXTRACTOR.md` 1절과 같다). 좋은 결과:
1. 원문의 판단이 빠짐없이, 한 번씩, 원문 그대로 들어 있다 — a·b 중 원문에 맞는 쪽으로.
2. 같은 조건은 def 하나·이름 하나다(같은 식 = 같은 조건).
3. 갈린 곳마다 원문 근거가 `review` 에 있다.

채점 통과는 최소 조건이다. 채점을 피하려고 트리를 원문에서 멀어지게 하지 않는다.

## 1. 입력과 산출물

- 입력: **원문**(책 소스) · 플레이북 · 후보 `tree_candidates/<a|b>.json` · 규칙 목록 `tree_candidates/<a|b>.rules.json`
  (행동 → 판정 → 부품 구조와 `source_text`·`interpretation`) · `scenarios.json`(채점용 정답지) · `COND_DSL.md` · 이 문서.
- 산출물: `books/<slug>/tree.json` 하나(트리 + `review`) → `python -m checklist.cond fmt <파일>`.
- a·b·사례·코드·문서는 고치지 않는다. git 기록은 보지 않는다.

## 2. 비교 도구 — 무엇이 다른지 본다(도구는 계산만, 판단은 너)

실행 환경: `book-to-playbook` 폴더에서 `PYTHONIOENCODING=utf-8`, `PYTHONPATH="<jhts 경로>;."`(없으면 시세가 빈다).

- `python -m checklist.verify_tree <slug> --dump 6` → `books/<slug>/logs/disagree.json`
  - `tree_diff` (**먼저 본다**): 상품·칸마다 a·b 를 트리 모양 그대로 맞춘 것. 노드마다 `same` · `diff` · `only_a` · `only_b`.
    같은 종류 묶음(all/any/atleast/not)은 자식끼리 다시 맞춘다 — 뼈대가 같고 잎 하나만 다르면 그 잎만 `diff`.
    같은지는 정규화한 식으로만 판정한다(이름·문장 무관). 짝 맞춤(이름·심볼 뺀 모양·안쪽 겹침)은 힌트일 뿐이다.
    읽기 쉽게: `python -c "from checklist import verify_tree as vt; a=vt._load('<slug>','tree_candidates/a.json'); b=vt._load('<slug>','tree_candidates/b.json'); print(chr(10).join(vt.render_zone(vt.zone_diff(a,b,'<상품>','<칸>'))))"`
  - `pairing`: 조건을 평평하게 — `common`(같은 식) · `only_a` · `only_b`, `same_behavior_as` = 3년간 판정이 한 번도
    안 갈린 상대(식은 달라도 같은 뜻일 수 있다는 근거. 수동은 기계가 값을 모르니 근거가 없다).
  - `sections`: 식이나 동작이 다른 칸 — 갈린 날의 양쪽 값·조건별 그날 값·최근 시세.
- 매도 규칙(exit)·분할(sizing.tranches)은 식으로만 비교한다 — `tree_diff` 의 그 칸을 본다(매매 시뮬레이션 비교 없음).
- a·b 의 규칙 목록은 `source_text` 로 나란히 놓으면 같은 원문 문장을 각자 어떻게 옮겼는지 바로 보인다.

## 3. 판단 — 원문 기준

- `same` / `common` → 하나만 쓴다. 이름이 다르면 a·b 중 원문에 가까운 이름을 고른다.
- `diff` 잎 → 같은 자리를 둘이 다르게 썼다(예: a 는 지수 `$index`, b 는 상품 자신을 봄 · `"?"` 위치가 다름). 원문을
  확인해 맞는 쪽을 쓴다.
- `only_a` / `only_b` → 원문에 있다 → 넣는다 · 원문에 없다(지어냄, 또는 사례·예시의 숫자를 규칙으로 씀) → 뺀다 ·
  다른 쪽의 항목과 같은 뜻이다 → 한쪽만 쓴다.
- **a·b 의 식과 이름을 그대로 가져다 쓴다 — 새로 짓지 않는다.** 둘 다 원문과 어긋나 고칠 재료가 a·b 어디에도 없으면
  지어내지 말고 원문에 가장 가까운 쪽을 두고 **미해결로 보고**한다(재추출 대상).
- **판례 — 원문이 안 정한 갈림.** a·b 둘 다 원문에 어긋나진 않는데 갈린 경우(원문이 그 선택을 명시 안 함 — 예: "축소"의
  기준이 처음 물량인지 남은 물량인지). 원문 취지에 맞게 하나로 정하되, 이건 네가 정한 **관례**다 — `review.precedents` 에
  적고 §6 에서 따로 보고한다(진행자가 사용자 승인 후 지침으로 올려 다음 책부터 적용).
- 같은 조건은 def 하나에 한 번 쓰고 쓰는 곳은 참조한다. 참조 자리에 `label` 을 다시 달지 않는다.
  한 식 = 한 이름, 한 이름 = 한 식(검사기가 정지시킨다 — 이름을 떼거나 바꿔서 피하지 않는다).
- 판단 기준(숫자 지어내지 않기 · 사례 숫자는 규칙 아님 · 칸 정하기 · 매도 규칙 요건)은 `EXTRACTOR.md` 4~8절과 같다.

## 4. 최종 트리 쓰기

COND_DSL 5절 형식에 `source: {"book": "<slug>", "extractor": "심판"}`, 그리고 `review`:

```json
"review": {
  "sections": {"TQQQ.entry": {"winner": "a|b|custom", "why": "원문 근거(인용)", "cases": ["갈린 날 판단"]}},
  "exits": {"TQQQ": {"winner": "a|b|custom", "why": "..."}},
  "scenario_overrides": {"<사례 이름>": "사례가 원문을 잘못 읽은 이유(원문 인용)"},
  "fire_ack": {"<경고문 그대로>": "원문 그대로라 정상인 이유"},
  "precedents": [{"what": "원문이 안 정한 갈림", "decision": "정한 관례", "why": "원문 취지 근거", "propose_to": "EXTRACTOR.md|COND_DSL.md"}]
}
```

- `sections`: a·b 의 식이나 판정이 다른 **모든** "상품.칸"(매도는 `exits`). `winner` 가 `a`/`b` 면 그 칸은 그쪽과
  식이 같아야 한다(검사기가 본다). 섞었으면 `custom`.
- `scenario_overrides` · `fire_ack` 는 원문 근거가 있을 때만 — 정지를 지우는 용도로 쓰지 않는다.
- `unexpressed` 는 두 쪽에서 정말 옮길 수 없는 것만 합친다.

## 5. 채점과 반복

`python -m checklist.verify_tree <slug>` — 정지가 0 이 될 때까지 3~5 를 반복한다(경고는 남아도 되지만 하나씩 이유를 보고).

| 정지 | 뜻 | 고칠 곳 |
|---|---|---|
| 공통 직렬화 아님 | `fmt` 를 안 거침 | `python -m checklist.cond fmt <파일>` |
| 미심판 불일치 | 식이나 판정이 다른 칸(수동 차이 포함)에 `review` 기록 없음 | `review.sections`/`exits` 에 원문 근거로 결정 |
| 최종≠승자 | a/b 를 골랐는데 그 칸 식이 고른 쪽과 다름 | 트리나 기록을 고쳐 맞춘다(섞었으면 custom) |
| 같은 로직 다른 이름 | 한 상품 안에서 같은 식이 이름 둘 | a·b 이름 중 하나로 통일, def 하나 |
| 같은 이름 다른 로직 | 다른 두 조건이 한 이름(묶음이 자식과 같은 이름 등) | a·b 의 이름 중 서로 다른 것으로 가른다 |
| 같은 식이 두 번 정의됨 | 같은 조건의 본문이 두 벌 | def 하나로 쓰고 참조 |
| 판정이 완전히 같은 조건 | 식은 다른데 3년간 판정이 같은 조건 쌍 — a판·b판이 둘 다 남았을 가능성 | 같은 조건이면 하나로, 원문이 일부러 둘로 썼으면 `fire_ack` |
| 이름 없는 수동 · `(정성)` 아닌 문장 수동 | 수동 잎 규칙 위반 | a·b 에 맞는 형태가 있으면 그것으로, 없으면 미해결 보고 |
| 사례 불일치 | 원문 사례를 트리가 재현 못 함 | 트리가 원문과 다르면 트리를, 사례가 원문을 잘못 읽었으면 `scenario_overrides` |
| 비중 합 초과 | 상품 비중 합 > 100% | 모드 조건이 겹치는지 · 원문 비중 환산 확인 |
| 수동 사유 머리 없음(경고) | 문장 수동의 사유가 `저자 미명시:`/`데이터 없음:`/`연산 없음:` 로 시작하지 않음 | a·b 중 머리가 있는 쪽을 쓴다 |
| 쓰이지 않는 확인 기록(경고) | `fire_ack` 의 경고가 더는 안 뜸 | 그 항목을 지운다 |

## 6. 보고

지침 승격 후보)** · 미해결(a·b 어디에도 고칠 재료가 없는 것) · 도구 문제(코드는 고치지 말고 정확히 보고) · 채점 반복 횟수.
